# Duplicate matching: how often loose matching raises an alarm

Generated by `analysis/13_duplicate_false_alarms.py`; every figure is registered in `notes/numbers.md` under `da.*`. No rule was changed. Loose matching is
`find_posted_invoices(vendor, invoice_no, loose=True)` in `app/sap/adapter.py`: the same vendor and the same letters and digits, ignoring case, slashes, dashes and spaces.

## Result

Every invoice in `posted_invoices` was matched against the others: 11,075 rows, 10,856 distinct invoices once exact duplicate rows are collapsed (data-audit D11).

| Measure | Value |
|---|---|
| Invoices flagged by loose matching | **120** |
| Flag rate | **11.1 per 1,000 invoices** |
| Flagged by exact matching | 120 |
| Flagged by loose matching only | 0 |
| Distinct flagged pairs | 60 |
| Pairs with the same date and the same amount (check H13 would fail the bill) | 0 |
| Pairs with the same amount / the same date / the same work order | 0 / 1 / 34 |
| Flagged invoices with a duplicate-bill query in the register | 61 |
| Flagged invoices with no duplicate-bill query | 59 (49.2%; see the note below on why this overstates it) |
| **As at intake (one flag per pair): flags / with a query / false-alarm share** | **60 (5.5 per 1,000) / 60 / 0.0%** |
| Invoices with a duplicate-bill query that loose matching does not flag | 59 |

**What it says.**
- **Nothing extra.** Loose matching adds 0 invoices to what exact matching already flags: every invoice number in the extract is written in one form, so there is no near-duplicate for loose matching to find.
- **What is flagged is reused numbers.** All alarms are the same vendor with the same invoice number (D04), mostly on a different date and amount. 0 of 60 pairs share a date and an amount, so none would be failed by H13; they would be warned for a person to decide.
- **Counting every invoice, as asked,** 120 invoices are flagged and 59 (49.2%) have no duplicate-bill query. That figure overstates the false alarms: the flag is symmetrical, so both invoices of a pair are flagged, and the verifier's query sits on only one of them.
- **Counting as at intake**, one flag is raised per pair, when the second bill arrives: 60 flags (5.5 per 1,000 posted invoices). 60 of them have a duplicate-bill query on at least one of the two invoices and 0 have none: a **false-alarm share of 0.0%** if a query is taken as the truth. 1 pair has a query on both invoices, 59 on exactly one and 0 on neither.
- **The other direction is not measured here.** 59 posted invoices with a duplicate-bill query have no matching posted invoice, so no matching rule on this table could flag them (data-audit D05).
- **Direction of the error is unknown.** A flag without a query may be a missed duplicate or a harmless reused number; the data cannot say which.

## Limits

- This measures posted invoices only. Bills not yet posted are not in `posted_invoices` (data-audit D12), so duplicates among them are not counted.
- A duplicate-bill query is taken as the sign that a real duplicate or reuse was found. The register cannot show a duplicate that nobody queried.
- Loose matching is used at intake only. The backtest uses exact matching: see `backtest/replay.py`.
